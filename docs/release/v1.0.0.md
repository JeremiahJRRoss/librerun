# LibreRun 1.0

LibreRun is an educational software environment for teaching the
design, development and operation of AI agents using multiple
agent-development frameworks. Its scope is agent conception and
planning, framework selection, security, operating environments,
observability, evaluation and optimization; its architecture uses
Docker Compose or Podman Compose to orchestrate its containers within a
Linux virtual machine, and it runs on Linux only. At its centre is a
self-hosted chassis for AI agents, built for educational purposes: a
complete, working platform to learn from — how an agent is conceived,
what a framework gives it and what the platform gives instead, how a
run is observed, where the security boundaries lie, and what an agent
needs from the environment it runs in. The chassis is real, not a mock:
an intake wizard, a human approval gate, PII redaction before anything
is stored, per-step model configuration, reports, and one trace per
run. You bring the agent; LibreRun brings everything around it.

Agent conception and planning are taught in person. Evaluation and
optimization are taught with the chassis's own instruments — the
gateway, which is the LLM router every model call passes through, the
edge proxy, the cache, and the tracing and observability tools, all
designed to teach evaluation — and the pages that teach them are not
written yet, as the list below says.

**Status: the record of 1.0, certified on 2026-09-22 and never
published.** LibreRun's first public release is the beta,
[1.1.0-beta.1](v1.1.0-beta.1.md), which carries 1.0 and everything
planned for the public beta. This page stays as the record of what 1.0
promised and how it was certified. What it did not do yet, and the
roadmap, are the beta's now: one list and one roadmap are live, and the
headings below point at them.

## The three promises

### 1. Five minutes to a gated, traced run — no keys, no config

```bash
git clone https://github.com/JeremiahJRRoss/librerun.git && cd librerun
./scripts/demo.sh
```

The script builds the stack from source: 5 min 5 s on a clean machine
and 3 min 34 s on a fresh CI runner when 1.0 was certified, and within
fifteen minutes on an ordinary laptop. There are no published images to
start from: LibreRun is released as source. Sign in with the credentials
the script prints. Then take **+ New Run** → an agent card → **Try a
sample** → submit, watch the steps, **Approve** at the gate, read the
report and press **View trace**. Five agents ship in the box and all of
them run keyless, through the gateway's built-in stub provider:

- **VITA**, the demo agent that investigates cross-vendor integration
  failures;
- an **echo** reference agent;
- examples in **LangGraph**, **LlamaIndex** and the **Vercel AI SDK**.

A keyless run is not a mock. Every call still passes through
authentication, PII redaction, model resolution and the trace — only the
answer comes from a fixture.

### 2. Your agent in an hour, and the platform snaps in

```bash
pipx install "git+https://github.com/JeremiahJRRoss/librerun#subdirectory=cli"
librerun init my-agent --template langgraph
librerun up
librerun run --agent my-agent --wait
librerun battery --agent my-agent
```

`init` scaffolds the agent; `--template container-python` or
`container-ts` takes the container path instead. `up` rebuilds the stack
with the agent on the new-run page, `run --wait` follows its sample to
the end, and `battery` is the conformance battery: green means done.

There are two paths, and CI proves both on every change:

- **In-process.** A LangGraph graph runs inside the backend, through
  `librerun-langgraph`.
- **A container, in any language.** It speaks the
  [Run Contract](../authoring/Run_Contract_v1.md) over HTTP and
  server-sent events, with the `librerun-agent` Python SDK or the
  single-file TypeScript reference server as its starting point.

Either way, the agent gets the platform's services without building
them: PII redaction on demand, the model an admin chose for each step,
knowledge search, run storage and audit. Every model call goes through
the **LibreRun gateway**, so an agent never holds a provider key, and an
admin retargets a step in the UI with nothing restarted.
[`docs/authoring/Quickstart.md`](../authoring/Quickstart.md) is the hour
path end to end.

### 3. Every run is one trace, in the tool you already use

Jaeger is in the box. Each run is one tree rooted at the run, across
the approval gate: intake, every phase, every model call with its model,
tokens and cost, and the agent's own spans when it emits them. Every run
has an audit log, and PII is redacted before anything is stored. Tested overlays send the same logs
and traces to **Datadog**, **Elastic** or **Splunk**
([`docs/platform/Observability.md`](../platform/Observability.md)), and
any other OpenTelemetry backend is one exporter away.

## How 1.0 was certified

Two gates were run on the release candidate; the full measurements stay
in the development record. 1.0 was
certified on 2026-09-22 and never published: the first public release is
the beta, [1.1.0-beta.1](v1.1.0-beta.1.md), whose tree `scripts/prepare_public_repo.sh` proves
identical to the candidate the gates ran on.

- **G0, demo parity.** VITA's seven-step intake was walked step by step
  in a real browser, with the PII redaction preview on a real upload. Then came
  live progress, the approval gate, and the full report with its works
  cited for each vendor and its skills cited. The PDF exported, feedback
  was saved and the trace link was followed. `scripts/librerun_smoke.py`
  ran keyless on top of that.
- **D, the delight gate, on two clean machines.** One was the release
  batch's sandbox: every service as a process, the UI in headless
  Chromium, D2 to D13. The other was CI's container stack on a fresh
  runner: D1 built from source, D2 to D7 in a browser with Jaeger, and D8
  to D10 through the CLI's hour path per template. In both walks, every
  run's trace was one tree rooted at the run.
- **One defect broke a promise, and it is fixed in this release.** An
  email address at a domain no public-suffix list knows, such as
  `jsmith@corp.local` (the shape of an Active Directory user in an SSO
  log), was not redacted: the candidate's walk stored it raw. 1.0
  redacts an address at any domain, at every point that redacts.
  Smaller first-contact fixes landed with it: a stopped Docker is
  reported as stopped rather than missing, and the release notes lead
  with the highlights instead of stopping mid-list.

What the release batch could not do, it says: its sandbox could not pull
container images, so D1 on the release owner's machine, and a first walk
by a person who has never seen the project, were left for publication.
Since the release is source-only, there are no published images to time:
the beta measures D1 from source, in CI on its candidate and then on the
release owner's machine.

## Upgrading from a pre-1.0 deployment

- The platform noun is **run**: `/cases` answers 404, and responses carry
  `run_id` and `run_number`.
- Run numbers carry a per-tenant prefix, `RUN` by default.
- Volume and database names can be pinned to their old values.

[`docs/platform/Install.md`](../platform/Install.md) §10 walks through
each of these. The compatibility aliases 1.0 still carries, and the
release each one goes in, are listed under **Deprecated** in
[`CHANGELOG.md`](../../CHANGELOG.md).

## Security

PII redaction fails closed: when the detector is not ready, intake
refuses rather than storing unredacted text. Secrets are partitioned by
the process that reads them, and the gateway is the only process that
holds a provider key. [`docs/platform/Security.md`](../platform/Security.md)
is the model in full, with the gate behind each claim. Report a
vulnerability privately, as [`SECURITY.md`](../../SECURITY.md) says.
